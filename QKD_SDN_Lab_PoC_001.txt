# IIT Delhi QKD SDN Lab PoC — Complete Roadmap

## Grounding in Tokyo QKD Network reality

The 2011 Sasaki et al. paper gives you the exact blueprint: their 3-layer architecture (quantum → key management → communication) at 45km fiber links achieved 61 kbps SKR (NEC/SSPD) and 300 kbps (Toshiba). More critically, their **eavesdropping detection + rerouting in seconds** during a live TV conference is what you're replicating at lab scale. The codebase above implements the identical 3-layer design.

## Phase 1 — Environment Setup (Day 1, ~3 hours)

**On both machines (run as root):**

```bash
# 1. Clone the project
git clone <your-repo> ~/qkdn_iitd
cd ~/qkdn_iitd

# 2. Set node identity (CRITICAL — different on each machine)
# Machine A:

export NODE2_HOST=192.168.1.20    # Machine B's actual IP

source .venv/bin/activate
pip install -r requirements.txt --break-system-packages
```

```bash
     -d '{"key_IDs": ["a3b2c1d0-..."]}' \
```

## Phase 7 — SDN Path Control Demo (Day 2)

Demonstrate the Tokyo QKD Network's rerouting capability:

```bash
# 1. Query live topology (shows ESKR on each link):

# Manually call the deactivation endpoint to simulate fiber cut:

curl -s http://127.0.0.1:7000/qkd/topology | python3 -m json.tool

# 5. Delete path cleanly:
```

## Phase 8 — Real QKD Hardware Integration (Week 3, if TAHQEECAT hardware available)

Switch from simulator to hardware with **one environment variable:**

```bash
# Set hardware mode:
export QKD_BACKEND=hardware
export QKD_HW_PORT=/dev/ttyUSB0    # or /dev/ttyACM0

# Verify your device is seen:
ls -l /dev/ttyUSB*
python3 -c "import serial; s=serial.Serial('/dev/ttyUSB0',115200); print(s.isOpen())"

# Restart node (hardware path activates automatically):
python node_runner.py --node node1
```

The `SerialQKDDevice` in `physical_layer/qkd_device_interface.py` sends:
```
AT+QKD:STATUS       ← device responds with QBER and key rate
AT+QKD:GENKEY=256   ← device runs BB84, returns hex key + QBER
```

Adapt `_parse_genkey_response()` to your vendor's exact command format. ID Quantique devices have Python SDK bindings; substitute the AT commands with `libidq` API calls in `generate_key_block()`.

## What This Demonstrates (Aligned to Tokyo QKD Network Paper)

The Sasaki et al. paper demonstrated three things live in October 2010. Your PoC replicates all three:

**1. Secure conferencing** — The `secure_messenger` and `secure_voip` apps use QKD-generated keys for AES-256-GCM (they used OTP). Every message or audio frame gets a fresh key from the fiber link. Key never leaves the KMS as plaintext.

**2. Eavesdropping detection** — The `_link_health_monitor` in the SDN agent continuously watches QBER. Inject `eavesdropper_intercept_prob=1.0` in `config.py` to simulate a full intercept-resend attack; you'll see QBER spike to ~27% (the theoretical BB84 detection signature) and the agent alerts the controller within one polling interval (10 seconds).

**3. Automatic rerouting** — The SDN controller's `_telemetry_poll_loop` detects QBER > 11% and calls `topology.deactivate_link()`. The next `best_single_path()` call then finds the alternate route. Post the path deactivation event to the SDN REST API to trigger this manually in the demo.

The entire pipeline runs on two laptops connected by an Ethernet cable — or any fiber you can pull across the lab — making this a fully reproducible, hands-on demonstration of exactly what the Tokyo network achieved at metropolitan scale, at IIT Delhi lab scale.
